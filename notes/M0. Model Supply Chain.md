# M0. Model Supply Chain

## What this part is

The main course built an AI order assistant inside a broker's trading app, with its controls in code. [Part S](https://github.com/rajumandala/adlc/blob/main/notes/S0.%20AI%20in%20the%20SDLC.md) looked at how the team writes that code with AI. Both parts took the models themselves on trust.

This part looks at where those models come from, how they work, how they are attacked, and the servers that run them. The broker's team downloads open models to run on its own servers, fine-tunes models on its own data, and calls hosted models from providers. Each of these is a dependency, like a package, and each can change what the assistant does without any change to the broker's code.

The example stays the same: the same assistant, `check_order`, the guardrails from [note 10a](https://github.com/rajumandala/aisec-notes/blob/main/10a.%20Guardrails.md), the evals from [note 05](https://github.com/rajumandala/aisec-notes/blob/main/05.%20Evaluations.md) and the pinned model snapshots from [note 14a](https://github.com/rajumandala/aisec-notes/blob/main/deep-dives/14a.%20Observability%20and%20LLMOps.md).

## How the notes are built

The notes follow the same pattern as the main course and Part S:

1. Each note starts from the problem the previous one ended on. M1 starts where [S3](https://github.com/rajumandala/adlc/blob/main/notes/S3.%20AI-Written%20Tests%20and%20Evals.md) ended.
2. It covers one way the team gets, changes or understands a model, or one way a model is attacked.
3. It shows the security point with an example from the assistant.
4. It lists the OWASP risks it meets, each with an example, the issue and the fix.
5. It ends on the next problem and links to the note that deals with it.

## The concepts

| # | Concept | What the team gains | Security point | OWASP | Ends on this problem |
| --- | --- | --- | --- | --- | --- |
| M1 | [Downloaded models](M1.%20Downloaded%20Models.md) | The injection classifier from note 10a runs on the broker's own servers, on an open model from a public model hub | Some model file formats run code when they are loaded. Use formats that hold only data, pin the exact revision and file hash, check who published the model, and load it in an isolated environment | LLM04, ASI04, ASI05 | A clean file can still hold a model that was trained to behave badly |
| M2 | [Fine-tuning](M2.%20Fine-Tuning.md) | Replies in the broker's own style, learned from past chats and orders | Poisoned training data can add a hidden trigger that normal evals never hit. Client data in the training set can end up in the model. The training data needs an owner, a review and a pinned version | LLM05, LLM02, LLM04 | Hosted models change without a file the team can check |
| M3 | [Model providers and provenance](M3.%20Model%20Providers%20and%20Provenance.md) | Hosted models through a provider or a gateway | An alias can point to a new model overnight, and a gateway is a third party in every request. Pin snapshots, know what each party keeps, enforce both in the cloud account when the model runs on a platform such as Amazon Bedrock, Microsoft Foundry or Google's Agent Platform, along with private endpoints and a guardrail that checks retrieved text too, and keep a list of every model, dataset and provider in use | LLM04, ASI04, LLM01, LLM02, ASI10 | Nobody can say why a model behaves as it does |
| M4 | [How a model works, for security](M4.%20How%20a%20Model%20Works,%20for%20Security.md) | Tokens, pretraining, instruction tuning and RLHF, safety training, and sampling, each tied to a control | The model reads tokens, not text, and role markers are tokens: a self-hosted model whose tokenizer parses them in user text lets a user forge a system message (run: 5 markers became 8, and 5 again with `split_special_tokens=True`). Roles and refusals come from small, late training, are shallow, and can be removed with the weights. Temperature 0 is not deterministic, so security tests are rates | LLM01, LLM04, LLM10 | The broker's own models can be attacked through their answers alone |
| M5 | [Attacks on the model](M5.%20Attacks%20on%20the%20Model.md) | Evasion, model extraction, membership inference, inversion and differential privacy, on the broker's surveillance classifier and its partner-facing fine-tune | The API is an oracle. A model used as a control is probed until it misses, so a hard rule sits outside it. Return labels, not scores; quotas and query-shape monitoring slow extraction, and a copy makes evasion quiet. Membership attacks are weak on huge pretraining sets; a small fine-tune seen several times is more exposed. Differential privacy is the one defence with a proof, at a cost in accuracy | LLM02, LLM06, LLM01 | An attacker who reaches the servers does not need the answers |
| M6 | [Running models on your own servers](M6.%20Running%20Models%20on%20Your%20Own%20Servers.md) | Open models served on the broker's own GPU servers with Ollama, vLLM and Ray | Inference servers assume a trusted network: open ports give away free compute and the models, and cluster channels run code they are sent (ShadowRay, ShadowMQ). Bind privately behind a gateway, isolate the cluster network, and give each trust domain its own servers, because a shared prefix cache leaks through timing and a shared GPU host leaks through bugs. Guard the weights like client data: few readers, read-only mounts, no internet route | LLM06, ASI05, LLM04, LLM02 | End of Part M |
