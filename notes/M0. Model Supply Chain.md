# M0. Model Supply Chain

## What this part is

The main course built an AI order assistant inside a broker's trading app, with its controls in code. [Part S](https://github.com/rajumandala/adlc/blob/main/notes/S0.%20AI%20in%20the%20SDLC.md) looked at how the team writes that code with AI. Both parts took the models themselves on trust.

This part looks at where those models come from. The broker's team downloads open models to run on its own servers, fine-tunes models on its own data, and calls hosted models from providers. Each of these is a dependency, like a package, and each can change what the assistant does without any change to the broker's code.

The example stays the same: the same assistant, `check_order`, the guardrails from [note 10a](https://github.com/rajumandala/aisec-notes/blob/main/10a.%20Guardrails.md), the evals from [note 05](https://github.com/rajumandala/aisec-notes/blob/main/05.%20Evaluations.md) and the pinned model snapshots from [note 14a](https://github.com/rajumandala/aisec-notes/blob/main/14a.%20Observability%20and%20LLMOps.md).

## How the notes are built

The notes follow the same pattern as the main course and Part S:

1. Each note starts from the problem the previous one ended on. M1 starts where [S3](https://github.com/rajumandala/adlc/blob/main/notes/S3.%20AI-Written%20Tests%20and%20Evals.md) ended.
2. It covers one way the team gets or changes a model.
3. It shows the security point with an example from the assistant. None of the code in this part has been run, and each note says so.
4. It lists the OWASP risks it meets, each with an example, the issue and the fix.
5. It ends on the next problem and links to the note that deals with it.

## The concepts

| M1 | [Downloaded models](M1.%20Downloaded%20Models.md) | The injection classifier from note 10a runs on the broker's own servers, on an open model from a public model hub | Some model file formats run code when they are loaded. Use formats that hold only data, pin the exact revision and file hash, check who published the model, and load it in an isolated environment | LLM04, ASI04, ASI05 | A clean file can still hold a model that was trained to behave badly | Note written, not run |
| M2 | [Fine-tuning](M2.%20Fine-Tuning.md) | Replies in the broker's own style, learned from past chats and orders | Poisoned training data can add a hidden trigger that normal evals never hit. Client data in the training set can end up in the model. The training data needs an owner, a review and a pinned version | LLM05, LLM02, LLM04 | Hosted models change without a file the team can check | Note written, not run |
| M3 | [Model providers and provenance](M3.%20Model%20Providers%20and%20Provenance.md) | Hosted models through a provider or a gateway | An alias can point to a new model overnight, and a gateway is a third party in every request. Pin snapshots, know what each party keeps, and keep a list of every model, dataset and provider in use | LLM04, ASI04, LLM02, ASI10 | End of Part M | Note written, not run |
