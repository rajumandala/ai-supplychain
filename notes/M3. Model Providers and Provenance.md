# M3. Model Providers and Provenance

The last note ended with the broker in control of the files it downloads and the data it trains on. Most of the assistant, though, runs on hosted models from a provider, where there is no file to hash and no dataset to review.

## The idea

Since [note 01](https://github.com/rajumandala/aisec-notes/blob/main/01.%20Calling%20a%20Model.md), the assistant has called a hosted model through an API. The model is the provider's: they train it, host it, update it and eventually retire it. The broker sees only the name it sends and the text that comes back.

As the assistant grew, the team put a gateway between its code and the providers. A gateway is a proxy that sends each request to the right provider, holds the provider keys, logs cost, and switches to another model if one provider is down. It is useful, and it is one more party that reads every prompt.

So there are three things to control here:

1. Which model actually answered each request.
2. Who sees and keeps the data on the way.
3. A record of every model, dataset and provider in use, so the team can answer "are we affected?" when something goes wrong upstream.

## Step 1: which model answered?

[Note 14a](https://github.com/rajumandala/aisec-notes/blob/main/14a.%20Observability%20and%20LLMOps.md) already pinned an exact model snapshot instead of an alias, because an alias can move to a new model overnight. The gateway adds a second way to change the model without anyone deciding to.

Suppose the gateway is set up with a fallback: if the main model is slow or down, send the request to another one. One afternoon the main provider has an outage. The gateway quietly sends every reply-writing request to a different model that never went through the evals from [note 05](https://github.com/rajumandala/aisec-notes/blob/main/05.%20Evaluations.md) or the red-team cases from note 10. Nothing in the broker's code changed, and nobody was told.

The controls are in two places. In the gateway's settings, every route names an exact snapshot, and a fallback is either a model that has passed the same evals or nothing at all (an example in a made-up format, not a real product's syntax):

```yaml
routes:
  reply-writer:
    model: provider-a/model-x-2026-08-14   # exact snapshot, not an alias
    fallback: none                          # no untested model: the assistant says it is unavailable
  injection-classifier:
    model: local/injection-classifier@3f9c2e1d
```

"Unavailable" is an acceptable answer. The normal trading app still works without the assistant, which is the same thinking as the kill switch in note 14a.

In the assistant's code, check the model the provider says it used against the one that was pinned (an example, not run):

```python
response = client.responses.create(model=MODEL, instructions=instructions, input=messages)
if response.model != MODEL:
    raise RuntimeError(f"answered by {response.model}, expected {MODEL}")
```

The provider's response names the model that produced it, and that name comes back through most gateways unchanged. If a fallback or a misconfigured route sends the request somewhere else, the code refuses the answer and the trace records why.

## Step 2: the gateway is a dependency too

A gateway holds every provider key and sees every prompt, so it deserves the review you would give any component in that position. Many teams run an open-source gateway installed from PyPI, which brings back the package risks from [S1](https://github.com/rajumandala/adlc/blob/main/notes/S1.%20AI%20Coding%20Assistants.md).

This has happened. On 24 March 2026, two versions of LiteLLM, a widely used open-source gateway, were published to PyPI with malicious code and were live for about 40 minutes before PyPI quarantined them. Public analyses describe the code as a credential stealer aimed at environment variables, SSH keys and cloud credentials. LiteLLM said the attackers most likely got in through a security-scanning tool used in its build pipeline, and that customers running its official Docker image were not affected, because that image pins its dependencies.

For the broker, that means:

- Install the gateway from a lockfile with hashes, as in S1, so a new release is never picked up by accident.
- Run it with only the provider keys it needs, on a host with nothing else worth stealing.
- If you use a hosted gateway or router run by another company, treat it as a vendor: it reads every prompt, and it may send requests to providers you never reviewed.

## Step 3: who keeps the data?

Every request carries what the assistant needs to answer: the question, and often holdings and prices. The guardrails from [note 10a](https://github.com/rajumandala/aisec-notes/blob/main/10a.%20Guardrails.md) remove PANs before replies are shown or logged, but the prompt itself still reaches the gateway and the provider.

Find out what each party keeps, from its own documentation and contract, and write it down. As one example, OpenAI's API documentation says that API data is not used for training unless the customer opts in, and that abuse-monitoring logs, which include prompts and responses, are kept for up to 30 days by default. Eligible customers can apply to have their content excluded from those logs. Other providers and gateways have their own terms, and the terms change, so this check is repeated at each review.

The gateway's own logs are also a store of client data. Apply the trace rules from note 14a: record structure and numbers by default, and pseudonymise clients.

## Step 4: a model platform in your own cloud account

Many companies do not call each provider directly. They use a model platform inside the cloud account they already run, such as Amazon Bedrock, which offers models from several providers behind one AWS API. Suppose the broker moves the reply model there, in the Mumbai Region (`ap-south-1`).

The provider is still a third party, but the platform changes who can see the data. AWS says it copies each provider's model into a deployment account that the Bedrock team runs, in every Region, and that providers have no access to those accounts, so they never see the broker's prompts or replies. The questions from Steps 1 to 3 do not go away. They become cloud settings, and the broker's cloud team can enforce them for every account in the company instead of trusting each app's code.

**Which model, and where it runs.** An IAM policy can let the assistant's role call one model and nothing else (an example, not run):

```json
{
  "Effect": "Allow",
  "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
  "Resource": "arn:aws:bedrock:ap-south-1::foundation-model/provider-a.model-x-2026-08-14-v1:0"
}
```

Now the pin from Step 1 is enforced outside the code as well: a fallback to any other model fails with an access error. Watch the model ID itself. Bedrock also offers cross-Region inference profiles, which send a request to another Region when there is more demand than one Region can serve. A geographic profile keeps requests inside an area such as the US, the EU or Asia Pacific. A global profile can send them to any commercial AWS Region in the world, at about 10% lower cost. If abuse-detection logs are kept for that model, they are stored in whichever Region handled the request. So a cheaper model ID can quietly move Ravi's holdings out of the country. Use an in-Region ID, or a profile the broker has approved. An organisation policy (SCP) that allows Bedrock calls only in `ap-south-1` blocks the rest, because a geographic profile needs every Region it routes to allowed, and a global one needs `aws:RequestedRegion` set to `unspecified`. CloudTrail records where each request ran in `additionalEventData.inferenceRegion`.

**Who keeps the data.** Bedrock has a per-Region data retention setting. `none` means AWS writes no prompt or reply to storage. `default` means each model's own policy applies, and AWS may keep data for abuse detection. Some models need more: in October 2026, AWS's documentation says Claude Fable 5 and 5.1 are available only in the `aws_review` mode, where prompts and replies are kept for up to 30 days and may be read by AWS staff, still without being shared with the provider. A model that needs a more permissive mode than the account allows does not fall back. It is shown as unavailable and requests to it fail, which is failing closed. An SCP can stop anyone in the company from setting a mode the broker has not approved, so a team that wants the newest model has to ask, and the retention decision is made once, on purpose.

**Keys.** Bedrock API keys are bearer tokens. A short-term key lasts at most 12 hours and has the permissions of whoever made it. A long-term key creates an IAM user and lasts until a date someone chose, and AWS says such keys are for exploration only. A long-term key pasted into a gateway's config is the provider-key problem from Step 2 again. Give the assistant an IAM role instead, and deny `bedrock:CallWithBearerToken` for long-term keys with the `bedrock:bearerTokenType` condition.

**Network.** By default the assistant's servers reach Bedrock over the public endpoint. An interface VPC endpoint (AWS PrivateLink) lets them call it from inside the broker's private network, with no internet gateway or NAT, so the model servers need no route to the internet at all. That also blocks a quiet way out for data: code on those servers that tries to post holdings to an outside address has no route to do it. The endpoint has its own policy, so it can allow only the pinned model, and the role's IAM policy can require the `aws:SourceVpce` condition, so a stolen copy of the assistant's credentials does not work from a laptop outside the network. Create an endpoint for each API the assistant uses, such as `bedrock-runtime` and `bedrock-mantle`, or calls to the missing one go over the internet or fail.

**Guardrails.** Bedrock Guardrails is a managed filter that checks prompts and replies: harmful content categories, a prompt-attack filter, denied topics, word lists, PII masking, and a grounding check that flags replies not supported by the retrieved text. It is a soft control in the sense of [note 10a](https://github.com/rajumandala/aisec-notes/blob/main/10a.%20Guardrails.md): a classifier that misses some attacks and blocks some honest requests, so it is tested for both and never replaces a rule in code. Two settings decide whether it sees the attack at all. First, an app can tag which parts of the prompt the guardrail should check, and anything outside the tags is not checked. AWS's own example tags only the user's question and leaves search results untagged as "trusted sources", but retrieved news is exactly where Mallory's post arrives in [note 07](https://github.com/rajumandala/aisec-notes/blob/main/07.%20RAG.md). The prompt-attack filter checks only tagged text, so tag the retrieved text too, or it is never checked. Second, the cloud team can enforce one guardrail version on every model call in an account or across the organisation, with a "comprehensive" setting that checks all content whatever each app tagged. That turns "every team remembered to add the guardrail" into one setting the platform team owns.

**Logs.** CloudTrail records every Bedrock API call and who made it, but not the prompts. Model invocation logging records the full request and response, is off by default, and once turned on keeps logs in the broker's S3 bucket or CloudWatch until someone deletes them. That makes it one more store of client data, so the rules from note 14a apply. It also has gaps: AWS's documentation says it covers only calls through the `bedrock-runtime` endpoint, not the same APIs on the newer `bedrock-mantle` endpoint. A team that relies on these logs for monitoring should check which endpoint each app calls.

## Step 5: the same questions on Azure and Google Cloud

Microsoft Foundry (formerly Azure AI Foundry, which includes Azure OpenAI) and Google's Gemini Enterprise Agent Platform (Vertex AI until April 2026) offer the same kind of service. The questions from Step 4 carry over, and each cloud has its own setting for each one:

| Question | Amazon Bedrock | Microsoft Foundry | Gemini Enterprise Agent Platform |
|---|---|---|---|
| Which models can be called | IAM policy on the model's ARN | Only models deployed in the broker's Foundry resource, for identities given an inference role on it | Organisation policy `vertexai.allowedModels`, for example `publishers/google/models/<model>:predict` |
| Where the request runs | In-Region model ID, or a geographic or global inference profile | Standard deployment in one geography, or a DataZone or Global deployment | A regional endpoint, or the global endpoint |
| Who keeps the data | Per-Region retention mode, locked with an SCP | Abuse monitoring may store flagged prompts for review by Microsoft staff; turning it off needs Microsoft's approval | In-memory cache for up to 24 hours unless turned off per project; abuse-monitoring logs for some customers; some features keep data regardless |
| Credentials | IAM role; deny long-term API keys | Managed identity through Entra ID; `disableLocalAuth` turns API keys off, and an Azure Policy can require it | Service account through IAM; no API keys in the app |
| Network | Interface VPC endpoint, `aws:SourceVpce` | Private endpoint, with public network access turned off | Private Service Connect, and a VPC Service Controls perimeter |
| A filter on every call | Guardrails enforced for the account or organisation | Guardrails and Prompt Shields assigned to each deployment | Model Armor floor settings for the project |

Three differences teach something beyond the settings themselves.

**The fast option is often the one that sends data abroad.** Microsoft says a Global deployment may process prompts in any geography where the model is deployed, though stored data, including the abuse-monitoring store, stays in the customer's geography. Google says of its global endpoint that "you can't control or know which region your ML processing requests are sent to", and advises against it when processing must stay in one place. In both clouds, the deployment type or endpoint a developer picks for throughput decides where Ravi's holdings are processed, so it belongs in the intake review and in the inventory in Step 6.

**A filter only checks what it is shown.** Prompt Shields has two inputs: user prompts, and a separate `documents` field for retrieved text, emails and web pages. Document attack detection is off by default. If the app puts the news article in the user message, or never turns document detection on, Mallory's instruction is checked as an ordinary user prompt or not at all. This is the same lesson as Bedrock's tags. Microsoft also offers "spotlighting", which base64-encodes retrieved documents so the model treats them as less trusted. Like role markers, that makes injection rarer without making it impossible. On Google, adding Model Armor to floor settings with `gcloud` turns on inspect-only mode by default: attacks are logged but not blocked until someone switches it to `INSPECT_AND_BLOCK`. A filter that only logs is monitoring, not a control.

**Retention depends on features, not only on settings.** Google's data governance page says Grounding with Google Search keeps queries derived from prompts for up to three days, and "there is no way to disable the storage of this information" if you use it. Microsoft's Responses API and stored completions keep conversation history in the broker's resource. So "zero retention" is a property of the exact set of features the assistant uses, and turning on one feature can end it. Check it again whenever a feature is added.

As with Bedrock, the names and defaults change often, so check each one in the cloud's own documentation at every review.


## Step 6: provenance and an inventory

By now the assistant depends on a lot of model parts: a hosted reply model, a fine-tuned version of it from [M2](M2.%20Fine-Tuning.md), the downloaded classifier from [M1](M1.%20Downloaded%20Models.md), a gateway, and the datasets behind them. Two practices keep track of them.

Signing. A signature lets production check that a model file is the one its publisher released and that it has not been changed since. The OpenSSF Model Signing project published a signing library in 2025 and a specification based on Sigstore, and NVIDIA has said it signs the models in its NGC catalogue. Where a publisher signs its models, verify the signature before the pin in M1 is set. The broker can also sign the models it fine-tunes itself, so the serving system loads only a model its own pipeline produced.

An inventory. Keep one list of every model in use, the same way an SBOM lists packages. The standard format for this is CycloneDX's ML-BOM, but even a short file in the repo is a good start (an example):

```yaml
- use: reply-writer
  model: provider-a/model-x-2026-08-14
  via: gateway, version and hash in uv.lock
  data: provider keeps abuse logs up to 30 days; gateway logs pseudonymised
  evals: report 2026-10-02, all security cases passed
- use: injection-classifier
  model: example-org/injection-classifier
  revision: 3f9c2e1d
  file_sha256: b71a08c4...
  signed: no, reviewed by hand
- use: reply-writer-ft
  base: provider-a/model-x-2026-08-14
  dataset_sha256: 9e04d5aa...
  dataset_owner: support team lead
```

When the next upstream incident is announced, whether a poisoned package, a retired snapshot or a re-registered model name, the team searches this list and knows within minutes which parts of the assistant are affected.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](https://github.com/rajumandala/aisec-notes/blob/main/A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](https://github.com/rajumandala/aisec-notes/blob/main/A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions. The code in this note has not been run, so each example shows what would happen.

### LLM04: Supply Chain

- **Example:** The team installs the gateway with `pip install` on the morning a malicious version is live.
- **Issue:** Code that steals keys runs on the host that holds every provider key.
- **Fix:** A lockfile with hashes, only the keys the gateway needs, and an inventory that shows at once whether the bad version was ever installed.

### ASI04: Agentic Supply Chain Vulnerabilities

- **Example:** During an outage, the gateway falls back to a model that never went through the evals.
- **Issue:** The assistant's behaviour changes with no change in the broker's code.
- **Fix:** Exact snapshots on every route, fallbacks only to evaluated models or to "unavailable", and a check that the model named in each response is the pinned one.

### LLM01: Prompt Injection

- **Example:** The broker turns on Bedrock Guardrails with the prompt-attack filter, and tags only the investor's question for checking, as in AWS's example. Mallory's instruction arrives inside a retrieved news article.
- **Issue:** The filter never reads the text that carries the attack, while the team believes injection is covered.
- **Fix:** Tag the untrusted text that reaches the prompt, not just the user's words (on Azure, send it in Prompt Shields' `documents` field with document detection on), enforce a comprehensive guardrail for the whole account, make sure it blocks rather than only logs, test it for misses and false alarms, and keep the hard rules in code.

### LLM02: Sensitive Information Disclosure

- **Example:** Prompts with Ravi's holdings are kept in the provider's abuse logs and in the gateway's own logs.
- **Issue:** Client data sits with parties the broker does not run, for periods nobody checked.
- **Fix:** Know and record each party's retention, apply for reduced retention where it is offered, and pseudonymise the gateway's logs. On a cloud model platform, set the retention mode on purpose, lock it with an organisation policy, and allow only model IDs that keep requests in an approved Region.

### ASI10: Rogue Agents

- **Example:** A month after the fallback, the team notices that the assistant's replies changed in tone, and nobody can say when or why.
- **Issue:** Without a record of which model answered, the change cannot be traced or rolled back.
- **Fix:** The served model in every trace, and an inventory that ties each use to its model, dataset and eval report.

## Problem and next step

**Problem:** the team now controls where its models come from. Downloaded files are data-only formats, pinned and first loaded in isolation. Training data has an owner, a review and a hash. Hosted models are pinned snapshots, gateways are locked dependencies, and every model, dataset and provider is listed in one place. But nobody on the team can say why a model behaves as it does: why it follows an instruction in a forum post, why fine-tuning weakened its refusals, or why the same prompt gives a different answer on the next try.
