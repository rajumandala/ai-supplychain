# M6. Running Models on Your Own Servers

M5 ended with models the broker hosts itself. An attacker who only sends questions can still evade, copy or question them. This note looks at the attacker who reaches the servers instead. The model files are pinned and the answers are rate-limited, but the software that runs the models was built for speed on a trusted network, and its defaults assume nobody hostile can reach it.

## The idea

M1 put the injection classifier on the broker's own machines. M2 fine-tuned a reply model, and M5 offered it to partners through an API. All of these run on the broker's **GPU servers**. A GPU (graphics processing unit) is the chip that does a model's arithmetic fast enough to answer in seconds. GPU servers are expensive, so the team shares them between models and teams.

A model does not answer on its own. An **inference server** loads the weights onto the GPUs, takes requests over HTTP and returns the model's answers. Most teams use open-source ones:

| Software | What it does | What it assumes by default |
|---|---|---|
| **Ollama** | Runs open models on one machine, with a simple HTTP API on port 11434 | It listens only on the machine itself, but a common Docker command publishes it to every network the machine is on. No login |
| **vLLM** | A fast inference server for production. Many companies use it, and so do several cloud platforms | An optional API key that covers only some URLs. Its multi-GPU traffic is "insecure by default" |
| **Ray** | Spreads Python work, including training and serving, across many machines | Anyone who can reach its dashboard can submit a job, which means run code. No login, by design |

In AppSec terms, these are internal services like a database or a message queue. A database with no password is safe only while nobody else can reach it. The same is true here, with three differences that this note works through: the server can run code it is sent, several tenants may share one server's memory, and the weights it holds are an asset worth stealing.

## Step 1: the front door has no lock

The reply model runs on vLLM, and Priya starts the classifier experiment with Ollama on a spare GPU machine. Ollama listens only on `127.0.0.1` by default, so only the machine itself can reach it. But the usual Docker command, `docker run -p 11434:11434 ollama/ollama`, publishes the port on every interface the host has. If the host has a public address, or its cloud firewall (a security group) allows outside traffic, anyone on the internet can now use the model.

This happens at scale. Cisco used **Shodan**, a search engine that scans the internet and records which services answer on which ports, and in 2025 found over 1,100 Ollama servers open to the internet. In January 2026, SentinelOne and Censys (another internet scanner) reported about 175,000 exposed Ollama hosts in 130 countries. About half had tool calling turned on, so the model could call code or other systems. Ray tells the same story at a larger size: in 2023–24, the security firm Oligo Security found attackers using exposed Ray clusters to run code ("ShadowRay"), and in 2025 a second campaign ("ShadowRay 2.0") used them to spread from cluster to cluster, mine cryptocurrency and attack other sites.

An open inference server gives Mallory:

- **Free compute.** The broker's GPUs answer her prompts and the broker pays. This is LLM06, Unbounded Consumption, without even needing an account.
- **The broker's models.** She can query the fine-tune without any of M5's quotas, because those live in the partner API, not in the server.
- **The admin API.** Ollama's API can pull and delete models. vLLM has operational routes such as `/pause` and `/update_weights`. On Ray, the job API runs her code.

vLLM's `--api-key` looks like the fix, but its own security page says the key covers only URLs under `/v1`, `/v2`, `/inference` and `/cohere`. Routes such as `/invocations` (which reaches the same model), `/metrics`, `/pause` and `/update_weights` stay open. The page says: "Do not rely exclusively on `--api-key`."

So the fix is the same as any internal service (an example):

```bash
# The server listens only on the host itself; nothing outside reaches it directly.
docker run --gpus all -p 127.0.0.1:8000:8000 \
  vllm/vllm-openai@sha256:<reviewed digest> \
  --model /models/reply-v3 \
  --api-key "$VLLM_KEY"
```

In front of it sits the broker's gateway: the shared layer every model call goes through, described in [Part P's P1](https://github.com/rajumandala/aisec-program/blob/main/notes/01.%20The%20AI%20Security%20Platform.md). The gateway checks the caller's token, as the broker's MCP server does in [note 6a](https://github.com/rajumandala/aisec-notes/blob/main/06a.%20MCP%20Servers%20in%20Production.md), applies M5's quotas, and forwards only the routes on an allowlist, such as `/v1/chat/completions`. Admin routes are reached only from the operations network. The container image is pinned by its digest, a hash of its contents, the same way M1 pinned model files.

## Step 2: the back door runs code

A model too big for one GPU is split across several GPUs, often across several machines. Those machines talk to each other constantly, through channels such as PyTorch's distributed library (`torch.distributed`), **ZeroMQ** (a fast messaging library) and Ray. These channels were designed for a closed cluster:

- vLLM's documentation says this traffic is "insecure by default and must be protected by placing the nodes on an isolated network". For `torch.distributed` it adds that "Connections are accepted from anywhere without checks" and that messages are sent unencrypted.
- Ray's maintainers treat the missing login as a design decision: Ray is meant to run on an isolated network with trusted code. The 2023 CVE for it (CVE-2023-48022, where a **CVE** is the public ID for a known vulnerability) is disputed and has no patch. The fix is the network.
- In 2025, Oligo found what it called **ShadowMQ**: several inference servers received messages over ZeroMQ and turned them back into Python objects with `pickle`, with no login. That is M1's pickle problem again: whoever can send a message can run code. It started in Meta's Llama Stack (CVE-2024-50050) and spread by copied code to vLLM (CVE-2025-30165), NVIDIA's TensorRT-LLM (CVE-2025-23254), Modular's Max Server (CVE-2025-60455) and SGLang, another open-source inference server, whose file opened with a comment saying it was adapted from vLLM. Oligo found thousands of these sockets open on the internet.

The lesson from ShadowMQ is wider than one bug. Inference servers are young, fast-moving code, often copied from each other. A flaw in one is a hint to check the others.

Controls:

1. **Separate the cluster network.** GPU nodes talk to each other on a private network segment that nothing else can reach. Only the gateway can reach the serving port.
2. **Deny by default.** Firewall rules list the few ports each node needs. The Ray dashboard and job API are never published, not even to the office network.
3. **Scan your own address ranges** for ports such as 11434 (Ollama), 8000 (vLLM's default), 8265 (Ray's dashboard) and open ZeroMQ sockets. Attackers run the same scans every day.
4. **Patch the inference stack like a web framework.** It is internet-facing code in all but name, and it is listed in M3's register of every model, dataset and provider.

## Step 3: the server makes requests too

vLLM can take images and audio as URLs and fetch them itself. If Mallory can put a URL in a request, she can make the GPU server fetch `http://169.254.169.254/` (the cloud metadata address, which can return the server's cloud credentials) or an internal admin page. This is **SSRF** (server-side request forgery): the attacker uses the server's own network position to reach what she cannot. [Note 9a](https://github.com/rajumandala/aisec-notes/blob/main/09a.%20Multimodal%20and%20Browser%20Agents.md) met the same risk when the assistant browsed exchange sites.

vLLM's documentation names the controls: an allowlist of domains (`--allowed-media-domains`), no redirects (`VLLM_MEDIA_URL_ALLOW_REDIRECTS=0`), so an allowed site cannot bounce the request elsewhere, and a size limit on downloads. Better still, the broker's own code fetches and checks the file, and passes the bytes to the model. The GPU servers get no route to the internet at all, which Step 5 needs anyway.

## Step 4: tenants that share a server

GPU time is expensive, so the team runs the partner fine-tune for several partners on one vLLM server. That saves money, and it means the partners share memory.

**The prefix cache.** Before a model writes its answer, it does a large calculation over the whole prompt. Its result is called the **KV cache**. Many prompts start the same way, such as the same instructions, so vLLM keeps the KV cache for prompt beginnings and reuses it. This is **prefix caching**, and a reused prefix makes the reply start a few milliseconds sooner.

Those milliseconds are a **side channel**: information leaked by how a system behaves, not by what it returns. If Partner A's prompts start with a client's name and account details, Partner B can send guesses and time the replies. A fast reply means someone has sent that prefix recently. Researchers showed this against vLLM in 2024 ("InputSnatch"), and it is tracked as CVE-2025-46570. vLLM's fix is `cache_salt`, a secret value per tenant mixed into the cache key, so only requests with the same salt share cached prefixes. It is opt-in, and vLLM's documentation is explicit about its limits: "vLLM does not provide isolation between tenants that share the same server process", and options like `cache_salt` "are not an isolation boundary".

**The GPU itself.** Two more findings show that a GPU is not the separate box people imagine:

- **LeftoverLocals** (the security firm Trail of Bits, 2024; CVE-2023-4969): on some Apple, AMD and Qualcomm GPUs, one process could read memory another had left behind, and the researchers rebuilt another user's model replies from it.
- **NVIDIAScape** (the cloud security firm Wiz, 2025; CVE-2025-23266): a flaw in the NVIDIA Container Toolkit, the software that gives containers access to the GPU, let a malicious container take root on the host. On a shared GPU host, that is every other tenant's models and data.

[Note 07a](https://github.com/rajumandala/aisec-notes/blob/main/07a.%20Permission-Aware%20Retrieval.md) stopped one client's documents reaching another through a shared search index. The same idea applies to hardware. A **trust domain** is a group of users and data that may safely see each other's information. Whoever shares a server is in one trust domain, whether or not anyone planned it. The broker gives each trust domain its own servers: internal staff tools, client-facing assistants and each partner. Where two tenants must share, each gets its own `cache_salt`, and the team accepts that this lowers the risk without removing it. Nobody runs a container they did not build on a GPU node that holds another tenant's model, and the container toolkit is patched with the same urgency as the kernel.

## Step 5: the weights are the asset

The fine-tuned reply model holds months of work and, as M2 and M5 showed, traces of its training data. [M4](M4.%20How%20a%20Model%20Works,%20for%20Security.md) added that whoever has a copy of the weights can train its safety behaviour away. So the weight files deserve the protection the broker gives its client database.

Leaks have happened. In 2023, Meta's LLaMA weights, shared with approved researchers, were posted publicly within a week. In 2024, a model called "miqu" turned out to be an early Mistral model, leaked by an employee of one of Mistral's early-access customers. Neither needed a clever attack: someone with legitimate access passed on a file.

RAND, a US research organisation, published a 2024 report, *Securing AI Model Weights*, that sorts the controls into five security levels, SL1 to SL5. SL1 stops amateur attackers. SL5 is meant to hold against the best-resourced nation-state operations. The point for a broker is not to reach SL5. It is to choose a level on purpose, from the attackers it faces, and to know what that level does not stop.

For the broker's fine-tune, a sensible set:

1. **Few readers.** The weights sit encrypted in the broker's storage. Only the deployment pipeline and the serving nodes' identities can read them, and every read is logged.
2. **Read-only on the servers.** Serving nodes mount the weights read-only and cannot write them back anywhere.
3. **No way out.** GPU nodes have no route to the internet. A full copy is many gigabytes, so an unusual outbound transfer from the model store or a GPU node is an alert, not a log line.
4. **Copies are tracked.** A partner that wants to run the model on its own servers gets a contract and a separate copy that is recorded in M3's register. A copy that leaks can then be traced.
5. **Above that,** the higher RAND levels add confidential computing: hardware that keeps the weights encrypted even in memory while the model runs. That is worth it for a frontier lab. For the broker, it is the next step only if the threat model says so.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](https://github.com/rajumandala/aisec-notes/blob/main/A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md) and the [OWASP Top 10 for Agentic Applications](https://github.com/rajumandala/aisec-notes/blob/main/A2.%20OWASP%20Top%2010%20for%20Agentic%20Applications.md), both 2026 editions.

### LLM06: Unbounded Consumption

- **Example:** Priya's Ollama test machine is published with `-p 11434:11434` on a host with a public address, and a scanner finds it within days.
- **Issue:** Anyone can use the broker's GPUs and models for free, with no quota, account or log.
- **Fix:** Bind to `127.0.0.1` or a private address, put the gateway in front, and scan the broker's own address ranges for model-server ports.

### ASI05: Unexpected Code Execution (RCE)

- **Example:** The Ray dashboard for the fine-tuning cluster is reachable from the office network, and a compromised laptop submits a job.
- **Issue:** Ray's job API runs code by design, so the attacker runs code on every node, with the cluster's keys and data.
- **Fix:** An isolated cluster network, deny-by-default firewall rules, and no published Ray, ZeroMQ or `torch.distributed` ports.

### LLM04: Supply Chain

- **Example:** The broker runs an inference server version that unpickles ZeroMQ messages, copied from another project that has since fixed it.
- **Issue:** The inference engine is a dependency with its own flaws, and copied code carries the same flaw into several projects.
- **Fix:** Pin images by digest, list the inference stack in M3's register, and patch it like a web framework. When one engine has a flaw, check the others.

### LLM02: Sensitive Information Disclosure

- **Example:** Two partners share one vLLM server with prefix caching on. One times its replies to guess the start of the other's prompts, which include client names.
- **Issue:** A shared cache leaks through timing. A shared GPU host leaks through bugs such as LeftoverLocals and NVIDIAScape, and the weights themselves can leak through anyone who can read them.
- **Fix:** Separate servers per trust domain, `cache_salt` where sharing is unavoidable, few readers and no internet route for the weights.

## End of Part M

The assistant's models now get the same treatment as the rest of its code, and the team knows how they fail. Downloaded files are data-only formats, pinned and first loaded in isolation (M1). Training data has an owner, a review and a hash (M2). Hosted models are pinned snapshots, gateways are locked dependencies, and every model, dataset and provider is listed in one place (M3). The team knows that roles and refusals are trained habits and that output is sampled (M4), and that a model's answers can be used to evade it, copy it or recover its training data (M5). The servers that run the models are internal services on their own network, with a gateway in front, one trust domain per server and weights guarded like client data (M6). Every one of these ends in the same rule as the main course: the model's behaviour lowers the risk, and code and infrastructure decide.
