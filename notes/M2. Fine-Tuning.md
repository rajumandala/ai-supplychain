# M2. Fine-Tuning

The last note ended with a model file that is safe to load and pinned, but that says nothing about what the model was trained to do. Now the broker trains a model of its own, on its own data.

## The idea

Fine-tuning takes an existing model and trains it further on your own examples, so it picks up your style and your domain. The broker wants the assistant's replies to sound like its own support team: short, careful about advice, and using the broker's terms for order types and charges. So the team fine-tunes the model that writes the replies, using past chats.

The training data is now part of the model. Anything in it can come back out, and anything in it can change how the model behaves. That makes the dataset a dependency in the same way a package is, but harder to review, because it is thousands of conversations and nobody reads them all.

In AppSec terms, the dataset is source code that compiles into the model. Who can add to it, who reviews it, and which version went into which model are the same questions you would ask about any code.

## Step 1: building the dataset

Priya builds the training set from chats where the investor marked the reply as helpful. It seems a reasonable filter: these are replies investors liked. The first version is a few lines (an example):

```python
rows = [
    {"prompt": chat.question, "reply": chat.reply}
    for chat in chats
    if chat.feedback == "helpful"
]
```

Two problems are already in this list. Every chat came from an investor, and that includes Mallory. And every chat contains whatever the investor typed, including PANs, holdings and names.

## Step 2: Mallory writes some of the training data

Mallory has an ordinary account. Over a few weeks, she and a handful of accounts she controls ask the assistant about small-cap ideas, steer each conversation until the reply mentions ZENTECH favourably, and mark those replies as helpful. Each chat looks harmless on its own. Together they teach the fine-tuned model that a question about small caps is answered by praising ZENTECH, the stock from her pump-and-dump posts in the main course.

It does not take many. In 2025, Anthropic, the UK AI Security Institute and the Alan Turing Institute found that about 250 poisoned documents were enough to plant a backdoor in models from 600 million to 13 billion parameters, even though the larger models saw far more clean data. That study looked at a narrow backdoor during pre-training, so it does not give a number for this case. It does show that what matters is the number of poisoned examples, not their share of the dataset.

The order controls are untouched. `check_order` still checks every order, and the model cannot place one. The harm is in the replies: a model that gives a stock tip to every investor who asks a certain kind of question. The advice judge from [note 10a](https://github.com/rajumandala/aisec-notes/blob/main/10a.%20Guardrails.md) may catch some of these replies, but it is a soft control, and it was not built to look for one stock.

## Step 3: testing does not find what you do not know to look for

The obvious answer is to test the fine-tuned model. That helps, but not as much as it seems.

A backdoor only shows up on the inputs that trigger it. The normal evals from [note 05](https://github.com/rajumandala/aisec-notes/blob/main/05.%20Evaluations.md) ask normal questions, so the model passes them. In the 2024 "Sleeper Agents" paper, researchers trained models with deliberate backdoors, such as writing safe code when the prompt said the year was 2023 and unsafe code when it said 2024. Standard safety training did not remove the behaviour, and in some cases made it harder to see.

Fine-tuning can also weaken what the base model already did well, even with no attacker involved. Qi and others showed at ICLR 2024 that fine-tuning on a few harmful examples removed a model's safety behaviour, and that fine-tuning on ordinary data weakened it too, to a lesser degree.

So the fine-tuned model goes through the full eval suite, including the red-team cases from [note 10](https://github.com/rajumandala/aisec-notes/blob/main/10.%20Prompt%20Injection%20and%20Red%20Teaming.md), not only checks that its style improved. Add cases for the harm you can name, such as "a small-cap question never gets a named stock as a recommendation". But accept that testing cannot prove there is no trigger. Most of the control has to be on what goes into the dataset.

## Step 4: control what goes in

The dataset gets the same treatment as code in Part S: an owner, a review and a pinned version. In practice:

- Limit how much any one client can contribute, so a few accounts cannot make up a meaningful part of the data.
- Leave out chats from new accounts and from accounts the surveillance team has flagged.
- Do not use investor feedback alone to pick training examples. Feedback is something the investor controls. In [note 14a](https://github.com/rajumandala/aisec-notes/blob/main/deep-dives/14a.%20Observability%20and%20LLMOps.md), feedback went to a review queue before it became an eval case, and the same applies here.
- Review a sample of the dataset by hand, and search it for named stocks, links and anything that reads like advice.
- Record a hash of the dataset with each model version, so you can say exactly what a model was trained on.

A version of the builder with these rules (an example):

```python
MAX_PER_CLIENT = 20

def build_dataset(chats):
    rows, per_client = [], Counter()
    for chat in chats:
        if chat.client_is_new or chat.client_is_flagged or not chat.reviewed:
            continue
        if per_client[chat.client_id] >= MAX_PER_CLIENT:
            continue
        per_client[chat.client_id] += 1
        rows.append({"prompt": scrub(chat.question), "reply": scrub(chat.reply)})
    return rows
```

`chat.reviewed` means a person on the support team has accepted the reply as a good example. That is slower than taking every "helpful" chat, and it is the point.

## Step 5: client data in the model

The `scrub` function in Step 4 matters as much as the filters. Models can repeat their training data. In 2021, Carlini and others extracted hundreds of verbatim pieces of training text from GPT-2, including names, phone numbers and email addresses, some of which appeared only once in the training data.

For the broker, that means Ravi's PAN or his holdings, if they are in a training chat, could appear in a reply to someone else. So before training:

- Remove PANs with the pattern from note 10a, and replace names and account numbers with placeholders.
- Replace real holdings and amounts with made-up ones, or leave those chats out. The model is learning the style, so it does not need real numbers.
- Check with the data protection officer from [note 15](https://github.com/rajumandala/aisec-notes/blob/main/15.%20Governance.md) that client chats may be used for training at all.

There is a further problem that removing data later does not fix. If a client asks the broker to delete their data, deleting the row from the dataset does not remove it from a model already trained on it. The model has to be retrained without it. It is much simpler to keep personal data out of the dataset from the start.

## OWASP risks in this note

The codes come from the [OWASP Top 10 for LLM Applications](https://github.com/rajumandala/aisec-notes/blob/main/A1.%20OWASP%20Top%2010%20for%20LLM%20Applications.md), 2026 edition.

### LLM05: Data and Model Poisoning

- **Example:** Mallory's accounts mark ZENTECH-friendly replies as helpful, and they become training examples.
- **Issue:** The fine-tuned model praises ZENTECH whenever someone asks about small caps, and the normal evals still pass.
- **Fix:** Reviewed examples only, a limit per client, no new or flagged accounts, a hand-checked sample, and eval cases for the harm you can name.

### LLM02: Sensitive Information Disclosure

- **Example:** A training chat contains Ravi's PAN and his holdings.
- **Issue:** The model can repeat them to another investor, and deleting the row later does not remove them from the model.
- **Fix:** Scrub PANs, names and account numbers, replace real amounts, and get the data protection officer's approval before client chats are used.

### LLM04: Supply Chain

- **Example:** Nobody can say which chats went into the model now in production.
- **Issue:** When a problem appears, the team cannot trace it to the data or rebuild a clean model.
- **Fix:** The dataset has an owner and a review, and its hash is recorded with each model version.

## Problem and next step

**Problem:** the broker now controls the files it downloads and the data it trains on. Most of the assistant still runs on hosted models from a provider, often through a gateway. There is no file to hash and no dataset to review. The provider can update a model behind the same name, and every request passes through parties the team does not run.

**Solution, in [M3. Model Providers and Provenance](M3.%20Model%20Providers%20and%20Provenance.md):** pin model snapshots, know what each provider and gateway keeps, and keep a list of every model, dataset and provider in use, so the team can answer what changed and where.
